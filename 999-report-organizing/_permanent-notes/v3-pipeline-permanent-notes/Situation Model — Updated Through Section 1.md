## Core Explanation

> [!evidence] Situation Model — Updated Through Section 1
> **Key Entities:** Causal attribution (the core process); the attributor (the person constructing explanations); triggering conditions (unexpectedness, negativity, importance); Fritz Heider (foundational theorist); the internal/external distinction (first taxonomic axis).
> **Causal Map:** Triggering conditions → activate causal search → produce causal explanation → shape future action and emotion (mechanism previewed but not yet elaborated).
> **Structural Overview:** We have established the *when* and *why* of causal attribution — the conditions under which the process activates and the functional purpose it serves.
> **Evolution This Section:** Foundation laid. The process is purposive, selective, and asymmetrically triggered.
> **Emerging Patterns:** The asymmetry of activation (failure > success) creates vulnerability to distortion — a pattern that will recur.
> **Open Threads:** *What* structure do these causal explanations take once generated? How does the specific content of an attribution reshape emotion and expectancy? These questions drive the next section.

> [!evidence] Situation Model — Updated Through Section 1
> **Key Entities:** *Expert*, *novice*, *domain-typical configuration*, *random configuration*, *unit of perception*, *working memory capacity*.
> **Causal Map:** Prior knowledge → reorganization of perceptual ontology → recognition replaces analysis → working memory operates on fewer, larger units → superior performance on domain-typical material.
> **Structural Overview:** The phenomenon of expertise has been established. The puzzle is set: working memory capacity is constant, yet experts perform as if their capacity were vastly larger. The resolution must lie in what counts as one item.
> **Evolution This Section:** Established the empirical phenomenon and isolated the critical finding (the random-board control) that constrains all subsequent theoretical accounts.
> **Emerging Patterns:** Recognition vs. analysis distinction; the importance of domain-typicality; the constancy of raw capacity coexisting with the variability of effective capacity.

> [!evidence] Situation Model — Updated Through Section 1
> **Key Entities:** Two characterised processing modes — System 1 / Type 1 (autonomous, parallel, working-memory-light) and System 2 / Type 2 (controlled, serial, working-memory-heavy). The framework as a functional architecture, not a neuroanatomical map.
> **Causal Map:** Working-memory dependence determines speed, parallelism, depletability, and phenomenological flavour. Autonomy from working memory → speed and parallelism → System 1's characteristic features. Working-memory engagement → serial processing → effort phenomenology → depletion → System 2's characteristic features.
> **Structural Overview:** Asymmetric relationship — System 1 generates first; System 2 audits intermittently. Self-location is in the negotiated equilibrium, not cleanly in either mode.
> **Evolution This Section:** Established the framework's actual claims and dispelled the popular two-homunculi reading. Introduced the working-memory-dependence criterion as the architecturally fundamental distinction.
> **Emerging Patterns:** The framework's explanatory power comes from a single architectural fact (working-memory dependence) cascading into multiple observable differences.
> **Open Threads:** What the two systems actually look like operationally; how their interaction generates observable behaviour; whether the "system" framing is metaphor or model.

> [!evidence] Situation Model — Updated Through Section 1
> **Key Entities:** the deliberating actor; the goal intention; the action; the intention-behavior gap; the five failure modes (forgetting, distraction, competing impulses, motivational decay, executive overload); the deliberative and implementational subsystems.
> **Causal Map:** Goal intentions are formed reliably; their translation into action fails frequently; failures cluster at the moment of action initiation; the cause is not motivational weakness alone but architectural decoupling of deliberation from implementation.

> **Evolution This Section:** The report has named the puzzle, characterized its empirical signature, and reframed the self-regulation problem as a problem of cognitive engineering rather than willpower deployment.

> [!evidence] Situation Model — Updated Through Section 1
> **Key Entities:** The reader; the text; the *object-level reading machinery* (decoding, parsing, proposition assembly); the *meta-level monitoring machinery* (tracking whether comprehension is succeeding); processing fluency as an indirect monitoring cue.
> **Causal Map:** Text → object-level processing → reading experience (fluency, ease) → meta-level interpretation of that experience as evidence of comprehension → regulatory action (or its absence) → final encoded representation. The chain breaks down at the meta-level interpretation step, because fluency-as-cue is unreliable.
> **Structural Overview:** A two-layered cognitive architecture in which the upper layer (monitoring) inspects the output of the lower layer (comprehension processing) using imperfect indirect evidence.
> **Evolution This Section:** Established the phenomenon — silent comprehension failure — and identified its mechanism: monitoring relies on cues (especially fluency) that can be produced without comprehension being present.
> **Emerging Patterns:** A theme of *indirection* — the reader has no direct access to comprehension state and must infer it from surface signals.
> **Open Threads:** What is the architecture of the meta-level system that produces these inferences? What does the monitoring loop actually look like when it operates well? How can the unreliable fluency cue be supplemented or replaced with more diagnostic signals?

> [!evidence] Situation Model — Updated Through Section 1
> **Key Entities:** The Python interpreter (the executable that runs code), the PATH environment variable (the OS-level lookup table for executables), the VS Code Python extension (the intermediary that connects the editor to the interpreter), the VS Code integrated terminal (which inherits PATH from the OS but can be overridden by the extension).
> **Causal Map:** Installing Python places an interpreter on disk → checking "Add to PATH" makes the interpreter findable by the OS → installing the Python extension gives VS Code the ability to discover and select interpreters → selecting an interpreter in the status bar tells the extension which Python to use → the terminal session inherits this selection when launching scripts. Each link in this chain can break independently.
> **Structural Overview:** A three-layer architecture: OS (PATH) → VS Code Extension (interpreter selection) → Terminal (execution context). All three must agree for scripts to run correctly.
> **Evolution This Section:** Established the foundational infrastructure layer. All subsequent sections assume this chain is intact.
> **Emerging Patterns:** The theme of "independent systems that must be explicitly connected" will recur throughout this guide.
