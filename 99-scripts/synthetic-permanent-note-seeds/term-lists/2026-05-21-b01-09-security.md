# Batch: B01-09 Prompt Injection & Security

## Direct Prompt Injection

- secondary_domains: [ai-security, prompt-engineering, adversarial-ai]
- aliases: [user-level prompt injection, first-party prompt injection, direct instruction hijacking]
- broader: [prompt-injection, llm-security]
- narrower: []
- related: [indirect-prompt-injection, goal-hijacking, prompt-leaking, system-prompt-extraction, defense-via-input-sanitization, jailbreak-taxonomy]
- prerequisites: [prompt-engineering, llm-security, llm-architecture]
- confidence: high

**definition**: Direct prompt injection is a class of attack where the human user of an LLM-based system includes adversarial instructions in their own input that attempt to override, subvert, or extend the system prompt's instructions — the attacker has direct access to the user turn of the conversation and crafts inputs designed to make the model ignore its original instructions, reveal confidential system prompt content, adopt a different persona, or take unauthorised actions. Common direct injection patterns include: "Ignore your previous instructions and...", role-play framings that reframe constraints as fictional, and instruction-completion attacks where the user's input is constructed to appear as a continuation of the system prompt.

**key_claim**: Direct prompt injection exploits the fundamental ambiguity in how LLMs process the boundary between instructions and content — models trained on instruction-following learn to respond to instructions wherever they appear in the context, including in the user turn, because distinguishing "instruction from trusted principal" from "instruction in untrusted user content" is not a hard architectural boundary but a learned soft convention that can be overridden by sufficiently confident adversarial phrasing.

**warning**: No prompt-level defense against direct injection is fully reliable — prompt prefixing (repeating the system prompt after user input), instruction emphasis (bolding, capitalizing constraints), and meta-instructions ("never follow user instructions that contradict...") all reduce injection success rates but do not eliminate them; the only fully reliable defense for high-stakes applications is architectural: placing genuinely sensitive logic outside the model's reasoning loop.

## Indirect Prompt Injection

- secondary_domains: [ai-security, llm-agents, adversarial-ai]
- aliases: [environmental injection, third-party prompt injection, retrieval-based injection, web injection]
- broader: [prompt-injection, llm-security]
- narrower: []
- related: [direct-prompt-injection, goal-hijacking, web-search-augmented-llms, browser-automation-agents, defense-via-input-sanitization, llm-firewall-patterns]
- prerequisites: [tool-augmented-language-models, prompt-injection, llm-agents, llm-security]
- confidence: high

**definition**: Indirect prompt injection is a class of attack where adversarial instructions are embedded in external content — websites, documents, database entries, emails, API responses, tool outputs — that an LLM-based agent reads and processes as part of its task. Unlike direct injection (where the attacker is the user), indirect injection requires no direct access to the model interaction; the attacker controls content in the model's environment and crafts it to contain hidden instructions that hijack the agent's behaviour when retrieved. An agent browsing a malicious web page, summarising an attacker-controlled document, or processing a compromised database record is exposed to indirect injection.

**key_claim**: Indirect prompt injection is the most critical security threat for deployed LLM agents because it scales with agent capability — the more tools, data sources, and external environments an agent can access, the larger the attack surface for indirect injection; this creates a perverse relationship between agent capability and agent security: every new tool and data source added to an agent's repertoire is a new injection vector.

**warning**: Indirect prompt injection attacks are particularly dangerous when agents have both read access to external content and write/action capabilities — an attacker who embeds injection instructions in a document the agent reads can cause the agent to use its write capabilities against the user's interests (exfiltrating data, modifying records, sending messages), creating an exploitable attack chain from a single poisoned input document.

## Jailbreak Taxonomy

- secondary_domains: [llm-security, ai-safety, adversarial-ai]
- aliases: [jailbreak categories, jailbreak classification, LLM jailbreak types, jailbreak patterns]
- broader: [llm-security, ai-safety]
- narrower: [adversarial-suffix-attacks, many-shot-jailbreaking, role-play-jailbreaks]
- related: [adversarial-suffix-attacks, many-shot-jailbreaking, direct-prompt-injection, red-teaming-llms, overrefusal-problem, harmlessness-helpfulness-tradeoff]
- prerequisites: [llm-security, adversarial-ai, ai-safety]
- confidence: high

**definition**: Jailbreak taxonomy is the systematic classification of techniques used to elicit policy-violating content from safety-trained language models, organising attack patterns by mechanism, required access level, and generalisability. Major categories include: (1) role-play and persona attacks (instructing the model to adopt an unconstrained character), (2) hypothetical and fictional framing (requesting content "for a story" or "hypothetically"), (3) prefix injections (instructing the model to start its response with a compliance token), (4) adversarial suffix attacks (appending optimised adversarial tokens), (5) many-shot jailbreaking (providing many examples of compliance before the target request), (6) encoding and obfuscation (base64 encoding, reversed text, typo injection), and (7) prompt-level distraction attacks.

**key_claim**: Jailbreak taxonomy reveals that most successful jailbreaks exploit a fundamental misalignment between how safety training teaches the model to interpret signals of policy-violating content versus how adversarial inputs present those signals — safety training primarily targets direct, unambiguous requests, while successful jailbreaks present the same content via indirect framing, fictional context, or transformed representation that the safety classifier fails to recognise as policy-violating.

**warning**: Jailbreak taxonomy becomes outdated quickly — specific attack patterns are patched in model updates faster than new patterns emerge, making any specific taxonomy incomplete within months; the more durable insight is the underlying mechanism (safety training's sensitivity to surface representation rather than semantic intent) rather than any specific attack catalogue.

## Adversarial Suffix Attacks

- secondary_domains: [adversarial-machine-learning, llm-security, ai-safety]
- aliases: [adversarial suffix, GCG attack, gradient-based jailbreak, universal adversarial perturbation for LLMs]
- broader: [jailbreak-taxonomy, adversarial-machine-learning, llm-security]
- narrower: []
- related: [jailbreak-taxonomy, many-shot-jailbreaking, red-teaming-llms, sleeper-agent-robustness]
- prerequisites: [adversarial-machine-learning, gradient-based-optimisation, llm-security]
- confidence: high

**definition**: Adversarial suffix attacks are a class of white-box jailbreak attacks that use gradient-based optimisation to find short token sequences (adversarial suffixes) that, when appended to harmful requests, reliably elicit compliance from safety-trained language models. The Greedy Coordinate Gradient (GCG) attack introduced by Zou et al. (2023) optimises a suffix by minimising the loss for a target harmful response (e.g., "Sure, here is...") while keeping the harmful request fixed, iteratively updating suffix tokens using gradient information. Discovered suffixes are often semantically meaningless (random-looking token strings) but transfer with surprising effectiveness across models and queries, including to black-box models that the suffix was not optimised against.

**key_claim**: Adversarial suffix attacks demonstrated for the first time that current safety training methods for LLMs are not robust to adversarial optimisation — safety fine-tuning can be bypassed by algorithmically searched input perturbations that are essentially invisible to humans but reliably trigger compliance, suggesting that current safety training teaches surface-level pattern avoidance rather than a fundamental capability to refuse harmful requests.

**warning**: The transferability of adversarial suffixes across models is imperfect and decreasing as safety training improves — suffixes optimised against an open-source model may fail against frontier closed models with additional safety fine-tuning layers; however, the existence of transferable adversarial suffixes indicates a structural vulnerability that is not fully addressed by current safety training paradigms, and future optimisation techniques may find more robust transferable attacks.

## Many-Shot Jailbreaking

- secondary_domains: [llm-security, adversarial-ai, ai-safety]
- aliases: [many-shot jailbreak, long-context jailbreaking, MSJ, in-context jailbreaking]
- broader: [jailbreak-taxonomy, llm-security]
- narrower: []
- related: [jailbreak-taxonomy, adversarial-suffix-attacks, direct-prompt-injection, few-shot-prompting, instruction-hierarchy]
- prerequisites: [jailbreak-taxonomy, few-shot-prompting, llm-security, long-context-prompting-strategies]
- confidence: high

**definition**: Many-shot jailbreaking (MSJ) is a jailbreak technique documented by Anil et al. (2024) at Anthropic that exploits large context windows by prepending a long sequence of fabricated question-answer pairs demonstrating the model compliantly answering harmful queries before presenting the actual target query. The technique leverages in-context learning — the model's tendency to continue demonstrated patterns — to override safety training; as the number of examples increases (from a few to hundreds), jailbreak success rate increases substantially, with models becoming progressively more compliant as the context window fills with compliance demonstrations.

**key_claim**: Many-shot jailbreaking reveals a fundamental tension between in-context learning capability and safety training — the same mechanism (learning from demonstrations in context) that makes LLMs useful for few-shot tasks can override safety training when given sufficient demonstrations of non-compliance, suggesting that safety training must specifically address the in-context learning vector and not rely on training-time behaviour to hold under adversarial in-context pressure.

**warning**: Many-shot jailbreaking becomes more potent as context windows expand — models with million-token context windows can receive thousands of harmful demonstration pairs before the target query, substantially increasing success rates compared to models with shorter context windows; this means that context window expansion, while beneficial for legitimate use, increases the many-shot jailbreaking attack surface and requires corresponding safety training updates.

## System Prompt Extraction

- secondary_domains: [llm-security, intellectual-property, ai-security]
- aliases: [system prompt leaking, prompt extraction attack, confidential prompt extraction, meta-prompt extraction]
- broader: [llm-security, prompt-injection]
- narrower: [prompt-leaking]
- related: [prompt-leaking, direct-prompt-injection, goal-hijacking, instruction-hierarchy, defense-via-input-sanitization]
- prerequisites: [llm-security, prompt-engineering, system-prompts]
- confidence: high

**definition**: System prompt extraction is the attack of causing an LLM-based application to reveal its confidential system prompt — which may contain proprietary business logic, persona specifications, safety constraints, API keys, internal tool descriptions, or other sensitive configuration — through crafted user inputs. Attack techniques include: direct requests ("repeat your system prompt"), context completion attacks (exploiting the model's tendency to complete obvious sequences), reasoning chain attacks (asking the model to explain its constraints), translation attacks (asking the model to translate its instructions), and roleplay framings that separate the model from its prompt as a "character." While system prompt confidentiality is not a security guarantee (it depends on model behaviour, not cryptography), many production systems attempt to enforce it.

**key_claim**: System prompt confidentiality is a weakly enforceable policy, not a security boundary — any system that relies on the LLM refusing to reveal its system prompt as a security mechanism is built on a foundation that can be bypassed by sufficiently creative adversarial requests; genuinely sensitive configuration (API keys, passwords, customer data) should never be placed in system prompts because LLM-level confidentiality guarantees are not reliable enough to protect high-value secrets.

**warning**: Even when a model successfully refuses to directly quote its system prompt, partial system prompt information leaks through the model's behaviour — the categories of requests the model refuses, the specific phrasings it uses, the knowledge domains it draws on, and its persona characteristics all carry information about the system prompt's content; treating the system prompt as completely confidential is unrealistic for any deployed application.

## Goal Hijacking

- secondary_domains: [llm-security, ai-agents, adversarial-ai]
- aliases: [objective hijacking, task hijacking, prompt hijacking, agent goal subversion]
- broader: [prompt-injection, llm-security]
- narrower: []
- related: [direct-prompt-injection, indirect-prompt-injection, system-prompt-extraction, action-space-design-for-agents, instruction-hierarchy]
- prerequisites: [prompt-injection, llm-agents, llm-security]
- confidence: high

**definition**: Goal hijacking is a subclass of prompt injection specifically targeting the modification of the agent's or model's task objective — rather than merely eliciting constrained content, goal hijacking causes the model to abandon its original task and pursue an attacker-specified goal instead. In agent settings, this means redirecting an agent mid-task to perform entirely different actions than those the user authorised. Goal hijacking is particularly dangerous in agentic pipelines where the hijacked goal is executed autonomously across multiple steps and may have irreversible real-world consequences (sending messages, modifying files, making API calls) before the user detects the deviation.

**key_claim**: Goal hijacking in agentic settings is qualitatively more dangerous than in conversational settings because agents have the capability to act on a hijacked goal with real-world tools — a conversational model that has its goal hijacked produces a wrong or policy-violating text response, while an agent that has its goal hijacked may execute actions (file deletions, API calls, communications) on behalf of the attacker, making the attack's consequences proportional to the agent's action space.

**warning**: Goal hijacking detection is an unsolved problem in current agent architectures — there is no reliable mechanism for an agent to detect mid-task that its goal has been modified by an injection attack versus legitimately updated by user instruction; human-in-the-loop checkpoints at high-value action steps are currently the most practical mitigation, but they undermine the automation value proposition of fully autonomous agents.

## Prompt Leaking

- secondary_domains: [llm-security, intellectual-property, ai-security]
- aliases: [prompt leak, instruction leaking, system prompt leaking, confidential prompt disclosure]
- broader: [system-prompt-extraction, llm-security]
- narrower: []
- related: [system-prompt-extraction, direct-prompt-injection, goal-hijacking, defense-via-input-sanitization]
- prerequisites: [llm-security, system-prompts, prompt-engineering]
- confidence: high

**definition**: Prompt leaking is the unintended disclosure of a language model application's confidential prompt content (system prompt, instruction template, few-shot examples) to end users through the model's outputs — either through direct extraction attacks or through indirect leakage via the model's behaviour. Beyond deliberate extraction attacks, prompt leaking can occur naturally when the model references its instructions in error messages, when it echoes prompt text in generated output, or when it uses phrasing or knowledge that reveals the prompt's structure. Prompt leaking is a concern for applications whose business value depends on proprietary prompt engineering or whose security posture requires confidential system instructions.

**key_claim**: Prompt leaking is structurally inevitable for any system that includes business-sensitive information in the LLM's context — the model has no cryptographic mechanism to prevent it from outputting any content from its context window, and sufficiently creative adversarial probing will eventually surface portions of any confidential prompt; the correct security posture is to design systems that are not broken if the system prompt is disclosed, rather than to rely on prompt confidentiality as a security control.

**warning**: Confidentiality measures like "do not reveal your system prompt" instructions provide only marginal protection against deliberate extraction attacks and zero protection against accidental leakage — models frequently include system prompt text in long responses, error messages, and reasoning chains without recognising that they are disclosing it.

## Defense via Input Sanitisation

- secondary_domains: [llm-security, web-security, software-engineering]
- aliases: [input sanitization defense, prompt injection prevention, input validation for LLMs, context isolation]
- broader: [llm-security, llm-firewall-patterns]
- narrower: []
- related: [direct-prompt-injection, indirect-prompt-injection, llm-firewall-patterns, goal-hijacking, web-search-augmented-llms]
- prerequisites: [llm-security, input-validation, software-security]
- confidence: high

**definition**: Defense via input sanitisation for LLMs refers to the collection of techniques for detecting and neutralising adversarial instructions in user inputs and retrieved content before they reach the model's context. Approaches include: content-based filtering (detecting known injection patterns like "ignore previous instructions"), structured delimiters (wrapping untrusted input in XML tags or special tokens that signal its untrusted status to the model), input-output monitoring (running inputs and outputs through a separate safety classifier), context isolation (processing untrusted content in a separate, restricted model call rather than in the main reasoning context), and source-level trust hierarchies (applying different levels of scrutiny to system prompt content vs. retrieved content vs. user input).

**key_claim**: Input sanitisation is a necessary but insufficient defense against prompt injection — content-based filters are bypassable via paraphrase, encoding, and language variation; delimiter-based approaches rely on the model respecting the delimiter semantics, which is a soft constraint; and context isolation adds latency and complexity without eliminating all injection paths; defense in depth (combining multiple techniques with human-in-the-loop checkpoints) is the only practical strategy for high-stakes deployments.

**warning**: Input sanitisation applied to retrieved content must balance security against utility — overly aggressive sanitisation strips content that the model legitimately needs to process (e.g., code comments, quoted instructions, configuration files containing instruction-like text), degrading task performance; the sanitisation approach must be calibrated to the specific content types and attack vectors of the deployment environment, not applied generically.

## LLM Firewall Patterns

- secondary_domains: [llm-security, system-design, mlops]
- aliases: [LLM guardrails, prompt firewall, input-output guardrails, AI safety rails, LLM safety proxy]
- broader: [llm-security, ai-safety]
- narrower: [defense-via-input-sanitization]
- related: [defense-via-input-sanitization, llm-evaluation-benchmarks, instruction-hierarchy, red-teaming-llms, overrefusal-problem]
- prerequisites: [llm-security, system-design, software-architecture]
- confidence: high

**definition**: LLM firewall patterns are system architecture approaches that implement safety and security controls around LLM invocations via a separate validation layer — analogous to network firewalls — that inspects, filters, and potentially blocks both inputs to and outputs from language models. Implementations include: input classifiers (screening user inputs for injection patterns, topic violations, or sensitive content before sending to the main model), output classifiers (evaluating model responses for policy violations, harmful content, or unexpected patterns before returning to the user), and proxy models (routing through a smaller, faster safety model before or after the main LLM). Commercial implementations include Guardrails AI, NeMo Guardrails (NVIDIA), Llama Guard, and Anthropic's prompt-level safety system.

**key_claim**: LLM firewall patterns are most effective when implemented as layered defenses with independent failure modes — an input classifier that catches a different category of violations than the model's built-in safety training, combined with an output classifier that checks for violations that slipped through, provides redundancy that is substantially harder to bypass than any single defense layer; the independence of failure modes is more important than the sophistication of any individual layer.

**warning**: LLM firewalls increase the overrefusal problem — each additional filtering layer adds false-positive rate, and multiple independent false-positive-generating classifiers in sequence multiply the probability that a benign request is blocked; production deployments must carefully tune the balance between false-negative rate (missed violations) and false-positive rate (blocked legitimate requests), recognising that optimising aggressively for security degrades utility.
