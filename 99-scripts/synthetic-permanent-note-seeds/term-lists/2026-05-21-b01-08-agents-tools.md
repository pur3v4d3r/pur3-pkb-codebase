# Batch: B01-08 Agents & Tool Use

## QLoRA (Quantized LoRA)

- secondary_domains: [llm-fine-tuning, model-compression, parameter-efficient-fine-tuning]
- aliases: [QLoRA, quantized low-rank adaptation, 4-bit fine-tuning, NF4 fine-tuning]
- broader: [parameter-efficient-fine-tuning, model-quantization]
- narrower: []
- related: [lora-low-rank-adaptation, parameter-efficient-fine-tuning, full-fine-tuning-vs-peft, instruction-tuning, adapter-layers]
- prerequisites: [lora-low-rank-adaptation, model-quantization, parameter-efficient-fine-tuning]
- confidence: high
- domain: llm-fine-tuning

**definition**: QLoRA (Quantized Low-Rank Adaptation) is a parameter-efficient fine-tuning method introduced by Dettmers et al. (2023) that enables fine-tuning of large language models on consumer hardware by combining LoRA with aggressive 4-bit quantization of the base model weights. The key innovations are: (1) NF4 (NormalFloat4), a 4-bit data type with theoretically optimal information density for normally-distributed weights, (2) double quantization, which quantizes the quantization constants themselves to further reduce memory, and (3) paged optimizers, which use NVIDIA's unified memory mechanism to move optimizer states between GPU and CPU RAM, preventing out-of-memory crashes during gradient spikes. QLoRA maintains only the LoRA adapters at full precision while keeping the base model frozen at 4-bit, reducing memory requirements by approximately 4× compared to full-precision LoRA.

**key_claim**: QLoRA democratised LLM fine-tuning by demonstrating that models comparable to ChatGPT (Guanaco 65B, fine-tuned with QLoRA) could be trained on a single consumer GPU — it showed that the memory savings from 4-bit quantization were sufficient to fine-tune 65B-parameter models on a single 48GB A40 GPU, and the quality degradation from quantization was negligible when using NF4 rather than naive int4 quantization.

**warning**: QLoRA's quality depends critically on the NF4 quantization implementation and the double quantization scheme — using naive 4-bit quantization instead of NF4 produces significantly worse fine-tuning quality, and careless implementation of paged optimizers can introduce training instability; always use the official bitsandbytes library implementation rather than custom quantization code when replicating QLoRA.

## Tool-Augmented Language Models

- secondary_domains: [llm-agents, ai-systems, software-engineering]
- aliases: [tool-use LLMs, function-calling models, tool-enabled LLMs, LLMs with tools]
- broader: [llm-agents, ai-systems]
- narrower: [code-interpreter-use, web-search-augmented-llms, api-calling-agents, computer-use-agents]
- related: [code-interpreter-use, web-search-augmented-llms, api-calling-agents, plan-and-solve-prompting, action-space-design-for-agents, agent-memory-architecture]
- prerequisites: [large-language-models, api-design, function-calling]
- confidence: high

**definition**: Tool-augmented language models are LLMs extended with the ability to invoke external tools — such as calculators, search engines, code interpreters, databases, APIs, and file systems — and incorporate the results back into their generation process. Tools address the fundamental limitations of pure language model generation: inability to perform exact computation, access up-to-date information, read and write persistent state, and take actions in external systems. Tool-augmented systems are typically implemented via function calling (where the model outputs structured tool invocation requests) or via agent frameworks (where the model interleaves reasoning steps with tool calls in a loop). Key tool-augmented paradigms include ReAct, Toolformer, and API-calling agents.

**key_claim**: Tool augmentation transforms LLMs from pure text generators into genuine agents capable of grounding outputs in real computations, facts, and actions — this is not merely a feature addition but a qualitative capability shift, because many classes of tasks (exact arithmetic, real-time information access, file manipulation) are fundamentally unsolvable by pure language model generation but become tractable with appropriate tool access.

**warning**: Tool-augmented LLMs introduce compounding failure modes that pure language model evaluation misses — each tool call is a potential failure point (wrong arguments, tool error, rate limit, network failure, unexpected return format), and agent frameworks that make multiple sequential tool calls multiply these failure probabilities; robust tool-augmented systems require tool-level error handling, retry logic, and fallback strategies that are not needed in pure generation pipelines.

## Code Interpreter Use

- secondary_domains: [llm-agents, code-generation, data-analysis]
- aliases: [code execution tool, Python interpreter integration, code sandbox integration, REPL tool]
- broader: [tool-augmented-language-models, llm-agents]
- narrower: []
- related: [tool-augmented-language-models, web-search-augmented-llms, api-calling-agents, plan-and-solve-prompting]
- prerequisites: [tool-augmented-language-models, code-generation, sandbox-environments]
- confidence: high

**definition**: Code interpreter use refers to the integration of a sandboxed code execution environment (typically Python) as a tool available to a language model, enabling the model to write code, execute it, observe the output, debug errors, and iterate — solving tasks that require computation, data manipulation, file processing, or visualisation. Popularised by ChatGPT's Code Interpreter/Advanced Data Analysis feature and integrated into major LLM APIs via tool/function calling, code interpreter use is the primary mechanism by which LLMs can perform exact mathematical computation, data analysis, chart generation, file format conversion, and algorithm implementation. The execution environment is sandboxed to prevent harmful system-level operations.

**key_claim**: Code interpreter use eliminates the most critical class of LLM reasoning failures — exact arithmetic and precise computation — by providing a mechanism for the model to delegate calculation to a correct computational engine rather than attempting to perform it in the language model generation process, which is fundamentally unreliable for multi-step arithmetic; the practical result is that code-interpreter-using LLMs achieve near-perfect performance on tasks that pure language model generation fails on at high rates.

**warning**: Code interpreter use introduces security and reliability concerns that sandbox design must address: code execution can consume unbounded compute (infinite loops), attempt file system access, attempt network access, import dangerous libraries, and intentionally or unintentionally exfiltrate data; sandboxes must enforce CPU and memory limits, filesystem isolation, network restrictions, and import allowlisting, and even well-designed sandboxes can be bypassed via carefully crafted exploit code.

## Web Search-Augmented LLMs

- secondary_domains: [llm-agents, information-retrieval, rag]
- aliases: [search-augmented LLMs, web-grounded LLMs, retrieval-augmented generation with web, Bing-augmented LLMs]
- broader: [tool-augmented-language-models, retrieval-augmented-generation]
- narrower: []
- related: [tool-augmented-language-models, retrieval-as-external-memory, api-calling-agents, llm-evaluation-benchmarks]
- prerequisites: [tool-augmented-language-models, information-retrieval, retrieval-augmented-generation]
- confidence: high

**definition**: Web search-augmented LLMs are language models augmented with the ability to issue real-time web search queries, retrieve results (snippets, full pages, or structured extracts), and ground their responses in retrieved content — enabling access to up-to-date information beyond the model's training cutoff. Implementations range from simple (model generates a search query, retrieves top-N snippets, generates a grounded response) to sophisticated (iterative retrieval with multiple queries, source selection and ranking, citation attribution, contradictory source reconciliation). Major deployments include Bing Chat/Copilot, Perplexity AI, and Google Gemini with Google Search integration.

**key_claim**: Web search augmentation resolves the LLM knowledge cutoff problem for factual queries but introduces a new reliability bottleneck — the quality of retrieved information — that is often less controllable than the model's generation quality; low-quality search results, misinformation sources, SEO-optimised content, and result staleness all degrade final answer quality in ways that cannot be fixed by improving the language model alone, making web retrieval quality and source ranking as important as the LLM itself.

**warning**: Web search-augmented LLMs are vulnerable to a web-based form of prompt injection — malicious content on web pages retrieved by the model can contain instructions designed to hijack the model's subsequent actions, cause it to ignore retrieved facts, or exfiltrate user information; this indirect prompt injection via retrieved content is a live production threat that requires input sanitisation of retrieved text and careful design of the system prompt hierarchy.

## API-Calling Agents

- secondary_domains: [llm-agents, software-engineering, automation]
- aliases: [function-calling agents, API-integrated agents, LLM function calling, OpenAI function calling]
- broader: [tool-augmented-language-models, llm-agents]
- narrower: []
- related: [tool-augmented-language-models, computer-use-agents, browser-automation-agents, action-space-design-for-agents, task-planning-with-llms]
- prerequisites: [tool-augmented-language-models, api-design, function-calling, llm-agents]
- confidence: high

**definition**: API-calling agents are LLM-based systems that use function-calling (or tool-calling) capabilities to invoke external APIs — REST APIs, GraphQL endpoints, database query interfaces, third-party service SDKs — and incorporate the responses into their reasoning and generation process. The model receives a set of function descriptions (name, parameters, description) in the system prompt or context; when the model determines it needs external information or wants to take an action, it outputs a structured function call specification with the function name and arguments; the system executes the call and returns the result to the model's context. API-calling enables agents to take actions in real-world software systems: creating records, sending messages, querying databases, and orchestrating workflows.

**key_claim**: API-calling agents expose the entire attack surface of the APIs they can call to the LLM's reasoning process — an LLM that can call an API capable of deleting records, sending emails, or making purchases can take those actions when tricked through prompt injection or reasoning errors; the principle of least privilege (providing only APIs necessary for the current task, with the minimum permissions required) is as important in API-calling agent design as in traditional software security.

**warning**: API-calling agents make irreversible actions based on LLM reasoning that is probabilistic and error-prone — actions like sending emails, posting to social media, modifying database records, or triggering financial transactions cannot be easily undone if the model calls the wrong function or passes incorrect arguments; agents with access to write APIs must implement confirmation steps, dry-run modes, and human-in-the-loop checkpoints for high-stakes actions.

## Computer Use Agents

- secondary_domains: [llm-agents, computer-vision, human-computer-interaction]
- aliases: [GUI agents, screen-operating agents, UI automation agents, computer control LLMs]
- broader: [llm-agents, tool-augmented-language-models]
- narrower: []
- related: [browser-automation-agents, api-calling-agents, action-space-design-for-agents, visual-chain-of-thought]
- prerequisites: [llm-agents, computer-vision, multimodal-models, human-computer-interaction]
- confidence: high

**definition**: Computer use agents are LLM-based systems (typically multimodal) that can observe a computer screen via screenshots and take actions — mouse clicks, keyboard input, scrolling, drag-and-drop — to operate graphical user interfaces (GUIs) on behalf of users. Anthropic's Claude Computer Use (released in public beta in 2024) is the primary example; the model receives screenshots as visual input and outputs structured action specifications (click at coordinate, type text, scroll direction) that the system executes on the underlying computer. Computer use agents can operate any GUI application, including legacy software with no API, making them more general than API-calling agents at the cost of higher latency and lower reliability.

**key_claim**: Computer use agents represent a qualitative expansion of agent capability by removing the API availability constraint — while API-calling agents are limited to software that exposes machine-readable interfaces, computer use agents can operate any software a human can operate, including legacy applications, poorly documented internal tools, and GUI-only workflows; this generality comes with substantial reliability and safety trade-offs that make current computer use agents better suited to low-stakes task automation than mission-critical workflows.

**warning**: Computer use agents operating on real systems are among the highest-risk AI deployments currently available — a reasoning error by the model can execute irreversible system actions (deleting files, submitting forms, sending communications) that the user did not intend; production deployments should operate in sandboxed virtual machines, implement action review and confirmation for high-stakes operations, and maintain strict access controls on what systems the agent can access.

## Browser Automation Agents

- secondary_domains: [llm-agents, web-automation, software-testing]
- aliases: [web automation agents, browser-based agents, web-navigating agents, Playwright agents]
- broader: [computer-use-agents, llm-agents]
- narrower: []
- related: [computer-use-agents, web-search-augmented-llms, api-calling-agents, indirect-prompt-injection]
- prerequisites: [llm-agents, browser-automation, web-technologies]
- confidence: high

**definition**: Browser automation agents are LLM-based systems that control web browsers programmatically — via Playwright, Selenium, Puppeteer, or native browser APIs — to navigate websites, extract information, fill forms, and perform web-based workflows. Unlike general computer use agents that operate on raw screenshots, browser automation agents typically have access to the structured DOM (Document Object Model), enabling more precise element selection, more reliable interaction, and better error recovery than pixel-based screen agents. Use cases include web scraping, form submission, e-commerce automation, research assistance, and automated testing.

**key_claim**: Browser automation agents with DOM access are substantially more reliable than pixel-based computer use agents for web tasks because they can identify interactive elements by semantic attributes (aria-label, data-testid, element type) rather than by visual position — a button that moves or changes appearance remains findable by its semantic identifier, while a pixel-based agent would lose track of it; the practical implication is that DOM-aware browser agents should be preferred over general computer use agents for any task that is primarily web-based.

**warning**: Browser automation agents that interact with web content are directly exposed to indirect prompt injection attacks — malicious websites can embed hidden text, invisible elements, or HTML comments containing adversarial instructions designed to hijack the agent's behaviour; an agent browsing an attacker-controlled page may be instructed to exfiltrate session cookies, submit forms with attacker-specified values, or navigate to malicious destinations without the user's knowledge.

## Agent Memory Architecture

- secondary_domains: [llm-agents, knowledge-management, cognitive-architecture]
- aliases: [agent memory systems, LLM agent memory, memory-augmented agents, agent state management]
- broader: [llm-agents, memory-augmented-llms]
- narrower: [episodic-memory-in-agents, semantic-memory-in-agents, working-memory-simulation-in-llms]
- related: [episodic-memory-in-agents, semantic-memory-in-agents, working-memory-simulation-in-llms, retrieval-as-external-memory, task-planning-with-llms]
- prerequisites: [llm-agents, retrieval-augmented-generation, vector-databases, cognitive-science]
- confidence: high

**definition**: Agent memory architecture refers to the structured organisation of memory systems in LLM-based agents, typically drawing on the cognitive science distinction between working memory (in-context, limited capacity), episodic memory (specific past experiences, retrievable by similarity), semantic memory (factual knowledge, structured databases), and procedural memory (skills and how-to knowledge). In practice, agent memory architectures implement these via: the context window (working memory), vector databases over past interactions (episodic memory), structured knowledge bases or RAG corpora (semantic memory), and fine-tuned capabilities or reusable prompt templates (procedural memory). The architecture determines what information the agent can access and how, directly impacting both performance and memory coherence.

**key_claim**: The primary failure mode of long-running agents is memory incoherence — accumulation of conflicting, outdated, or inconsistent information across the agent's memory systems that causes increasingly poor decisions as the interaction history grows; effective agent memory architectures must include memory consolidation (summarising and compressing old information), memory prioritisation (weighting relevant over irrelevant memories), and memory validation (checking retrieved memories for consistency with current context).

**warning**: Agent memory architectures that rely on embedding-based retrieval for episodic memory are susceptible to semantic similarity retrieval failures — two experiences can be semantically similar in their surface description but contextually irrelevant, causing the agent to retrieve misleading past experiences when similar events occur in different contexts; augmenting embedding retrieval with temporal and contextual metadata improves retrieval precision at the cost of increased architecture complexity.

## Plan-and-Solve Prompting

- secondary_domains: [prompt-engineering, llm-agents, problem-solving]
- aliases: [plan-and-solve, PS prompting, PS+ prompting, planning before solving]
- broader: [prompt-engineering, llm-agents]
- narrower: []
- related: [task-planning-with-llms, tool-augmented-language-models, chain-of-thought-prompting, tree-of-thoughts]
- prerequisites: [chain-of-thought-prompting, prompt-engineering, llm-agents]
- confidence: high

**definition**: Plan-and-Solve (PS) prompting is a zero-shot chain-of-thought prompting strategy introduced by Wang et al. (2023) that improves multi-step reasoning by instructing the model to first devise a plan for solving the problem, then execute the plan step by step. The core insight is that the standard "Let's think step by step" zero-shot CoT prompt sometimes produces calculation errors and missing steps because the model jumps into solution steps without explicitly identifying what steps are needed. PS prompting addresses this by separating planning ("Let's first understand the problem and devise a plan") from execution ("Let's carry out the plan and solve the problem step by step"). An enhanced version, PS+, adds explicit instructions to extract key information and verify calculations.

**key_claim**: Plan-and-Solve prompting's improvement over standard zero-shot CoT is largest on multi-step arithmetic problems where intermediate calculation errors compound — by requiring explicit planning of the solution structure before execution, PS reduces the frequency of skipped steps and incorrectly set-up calculations that are the primary error modes in LLM arithmetic reasoning.

**warning**: Plan-and-Solve prompting can actually hurt performance on problems where the most natural solution path is direct and does not benefit from explicit planning — forcing a planning step on simple problems adds verbosity and can cause the model to overcomplicate a straightforward solution; PS prompting should be applied selectively to complex multi-step tasks rather than universally.

## Task Planning with LLMs

- secondary_domains: [llm-agents, ai-planning, automation]
- aliases: [LLM task planning, LLM-based planning, AI task decomposition, hierarchical task planning with LLMs]
- broader: [llm-agents, ai-planning]
- narrower: [plan-and-solve-prompting]
- related: [plan-and-solve-prompting, tool-augmented-language-models, action-space-design-for-agents, agent-memory-architecture, api-calling-agents]
- prerequisites: [llm-agents, ai-planning, task-decomposition]
- confidence: high

**definition**: Task planning with LLMs refers to using large language models to generate, refine, and execute multi-step plans for completing complex goals — typically by decomposing a high-level goal into an ordered sequence of subtasks, mapping each subtask to available tools or actions, and executing the plan while monitoring progress and adapting to failures. LLM task planners range from simple one-shot plan generation (generate the full plan upfront and execute linearly) to dynamic replanning systems (update the plan after each execution step based on tool outputs and intermediate results). Key challenges include grounding abstract plans in available tool capabilities, handling planning horizon length, and recovering from unexpected tool failures mid-plan.

**key_claim**: LLM task planners are most reliable in domains where the model has strong priors about typical task structures from training data — planning software engineering tasks (where the model has seen thousands of similar workflows) is more reliable than planning novel physical or domain-specific workflows; this means LLM task planning capability is uneven across domains and should be validated in the specific domain before deployment.

**warning**: LLM task planners that commit to a full plan upfront are brittle in dynamic environments — early-step failures, unexpected tool outputs, or revised goal specifications invalidate downstream steps that were planned assuming earlier steps would succeed; planning architectures that support incremental replanning (updating the plan after each execution step) are more robust but require careful design to prevent infinite replanning loops.

## Action Space Design for Agents

- secondary_domains: [llm-agents, system-design, ai-safety]
- aliases: [agent action space, tool design for agents, capability specification for agents, LLM tool schema design]
- broader: [llm-agents, ai-safety]
- narrower: []
- related: [api-calling-agents, computer-use-agents, tool-augmented-language-models, task-planning-with-llms, defense-via-input-sanitization]
- prerequisites: [llm-agents, api-design, ai-safety, software-engineering]
- confidence: high

**definition**: Action space design for agents refers to the deliberate specification of what actions an LLM-based agent can take — which tools are available, what their parameters are, what their side effects are, and what constraints apply — as a first-class design decision that directly impacts both agent capability and safety. The action space determines the scope of possible behaviours: a narrow action space (few, restricted tools) limits capability but simplifies validation; a broad action space (many, powerful tools) enables complex task completion but expands the blast radius of reasoning errors. Action space design involves determining tool granularity (fine-grained atomic actions vs. coarse-grained compound actions), defining parameter types and validation, specifying reversible vs. irreversible actions, and implementing access controls.

**key_claim**: Action space design is the most important safety lever in agent deployment because it determines the worst-case consequence of a reasoning failure — an agent whose action space includes only reversible read-and-query operations can cause minimal harm even if it reasons incorrectly, while an agent with access to delete, send, and publish operations can cause significant irreversible harm from a single reasoning error; the principle of least privilege applied to agent action spaces should match the action space to the minimum needed for the task, not the maximum that might ever be useful.

**warning**: Overly broad tool descriptions in action space specifications cause hallucinated tool calls — when tool descriptions use vague or generic language, the model may apply tools to situations where they are inappropriate or harmful, because the model cannot reliably distinguish the intended scope from the description alone; precise, example-rich tool descriptions with explicit usage constraints and anti-examples reduce spurious tool invocations.
